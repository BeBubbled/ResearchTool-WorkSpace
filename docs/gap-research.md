# 研究空白调研：问题驱动的方法演化树（完整版）

参数：$ARGUMENTS
（在 Claude Code 里作为斜杠命令使用时，参数会自动填进上一行；在聊天里直接粘贴时，请手动填写下面的「输入」一节。）

---

## 0. 输入

- 领域：【例如：深度学习的长期时间序列预测】
- 时间范围：【起始年份】至【今天 / 回测截止日期】
- 包含 / 排除：【例如：只看预测，不看分类；排除纯应用论文】
- 规模：【快速版 15–20 个节点 / 完整版 30–60 个节点】
- 模式：【正式调研 / 回测】。回测 = 只允许使用截止日期之前公开的论文，第 6 步改成核对截止日期之后的真实历史。
- 输出：【一份文档 / 一个文件夹（CSV + Markdown）】
- 读者：【我自己 / 导师 / 组会】。决定术语要解释到什么程度。
- 邻近领域及其术语（可选）：【例如：统计学的 conformal prediction、计量经济学的 GARCH 和协整】。没填时由第 1 步自动生成，在第一个确认点交给用户审核。

输入不全时：能从上下文推断的，自己推断并在报告开头写明；推断不了且会显著影响结果的（领域、范围），先问一次再开始。

## 1. 术语（全程统一使用，并在报告开头为读者解释）

| 术语 | 含义 | 例子 |
|---|---|---|
| 方法族 | 思路相近的一类方法 | Transformer 类：Informer、PatchTST |
| 分类表 | 综述里把方法分成几大类的那张图或表 | 按模型结构分为 MLP、CNN、RNN、Transformer、基础模型 |
| 节点 | 一篇方法论文 | PatchTST |
| 遗留缺陷 | 这个方法还做不到的事 | PatchTST 不考虑变量之间的关系 |
| 演化边 | “B 是为了解决 A 的某个缺陷而提出的” | Informer →（单个时间点信息太少）→ PatchTST |
| 分歧点 | 同一个缺陷，后来有多条不同的解决思路 | 变量关系：各自独立处理 vs 把变量当 token |
| 属性 | 一个能回答“能 / 不能”的能力问题 | 能输出预测区间吗？ |
| 属性矩阵 | 行是方法、列是属性的表，格子填 ✓ / △ / ✗ | — |
| 组合空白 | 两个（或三个）属性，没有任何方法能同时做到 | 能输出区间 × 能直接用于新数据集 |
| 正向追踪 | 查“后来谁引用了这篇论文” | Google Scholar 的“被引用次数” |
| 拼接测试 | 把两个现成方法简单接起来，看效果够不够 | 基础模型的预测 + 事后 GARCH |

## 2. 全程规则

1. **每个事实都要有来源。** 每条结论标注一种来源：「检索核对」（本次打开过页面）、「论文原文」（读过对应段落）、「已有知识」（未核对）。报告末尾集中列出所有「已有知识」项。
2. **日期用首次公开日期。** 以 arXiv 页面上的 Submitted on 为准，不用会议年份。
3. **检索记录。** 每次检索都写进检索记录表：日期｜检索词｜工具或网站｜时间过滤｜结果数｜相关论文。没有检索记录，不得声称“尚无人研究”。
4. **先定规则再看结果。** 属性的 ✓ 标准、空白的判定标准、排序打分标准，都在看到对应结果之前写下来，之后不修改。
5. **拿不准就给 △，不给 ✓ 也不给 ✗。** 既不把空白误填掉，也不凭空造出空白。找空白时 △ 不算覆盖（见第 5 步）。
6. **删掉的和没找到的也要写出来。** 被过滤的候选、判定为“已被解决”的候选、检索失败的情况，都保留在报告里。
7. **用读者的语言，少用代称。** 第一次出现的术语按第 1 节解释；每个表格前写一句话说明它告诉读者什么。

## 3. 执行环境

开始前检查当前环境有哪些能力，然后选择对应做法：

| 能力 | 有时这样做 | 没有时退而求其次 |
|---|---|---|
| 能用脚本访问外部 API | 用 arXiv API 按日期取论文；用 Semantic Scholar Graph API 取参考文献、引用列表和引用上下文（citation contexts）；用 OpenReview API 取审稿意见 | 用网页搜索和网页抓取逐篇查看 |
| 能写文件 | 每一步的中间结果存成 CSV（nodes.csv、edges.csv、matrix.csv、gaps.csv、search_log.csv），可以中断后接着做 | 中间结果保留在对话里，每步结束时完整输出一次表格 |
| 能运行代码 | 属性矩阵的空列、两两组合、三元组覆盖用代码计算 | 在表格里逐列、逐对手工检查 |
| 能启动子 Agent | 第 2 步分批并行读论文（每个子 Agent 5–10 篇）；第 6 步用一个**没看过前面推导过程**的子 Agent 专门反驳 | 自己做，并在报告里写明“验证未经独立复核” |
| 用户在场 | 停两次：第 1 步结束时，请用户确认节点清单和邻近领域术语对照表；第 4 步归纳出属性定义之后、填格子之前，请用户确认属性清单 | 按最合理的理解继续，并在报告开头写明做了哪些取舍 |

## 4. 步骤

### 第 1 步：找综述，确定方法族和节点清单

1. 检索“【领域】 survey / review / taxonomy”，只看最近两年，按引用数挑 3–5 篇综述。
2. 在每篇综述里找分类图或分类表（通常在第 2 节，标题带 Taxonomy 或 Overview），记下大类和每类的代表论文。
3. 合并几篇综述的分类，得到方法族清单。
4. 补漏：
    - 向前：读代表论文的参考文献。
    - 向后：查代表论文被谁引用。
    - 查各方法族在最近两届顶会实验对比表里反复出现的基线：反复被比较的，就是当时的主流。
5. 按规模挑节点。每个方法族至少 2 个；每个已知的缺陷，至少保留一个“专门解决它”的节点。
6. 同时记下各综述 future work 一节列出的开放问题，第 5 步要用。
7. 生成邻近领域术语对照表：本领域术语｜邻近领域｜对应术语（例如“预测区间”对应统计学的“conformal prediction”）。用户在输入里给出的直接收录，其余由 Agent 补充，第 6 步用它生成跨领域检索词。

产出：方法族表（方法族｜代表论文｜来自哪篇综述）、节点清单、邻近领域术语对照表。

**确认点 1**：把节点清单和术语对照表交给用户确认后再进入第 2 步。

### 第 2 步：填方法节点表

每篇论文只读四处：

| 读哪里 | 填进哪一列 |
|---|---|
| 摘要 | 核心思路（一句话） |
| 引言里以 However 开头、批评前人的那段 | 要解决的问题（针对哪个前人方法的哪个缺陷） |
| 相关工作一节的最后一两句（作者说自己和谁不同） | 演化边的父节点 |
| Limitations / Conclusion | 遗留缺陷（作者自述） |

“遗留缺陷”还要从两个外部来源补充，并分别标注来源类型：

- **他人指出**：引用这篇论文的后续论文中，含 however、fail、limitation、unlike、overlook 的引用句。有 API 时用 Semantic Scholar 的引用上下文；没有时用 Google Scholar 的“在引用文章中搜索”。
- **审稿指出**：顶会论文去 OpenReview 看审稿意见里的 Weaknesses 一栏。

节点表的列：名称｜首次公开日期｜链接｜要解决的问题｜核心思路｜关键假设｜遗留缺陷（自述 / 他人指出 / 审稿，各附来源）｜被谁改进｜来源可信度。

### 第 3 步：演化边与分歧点

1. 边表的列：父方法｜缺陷｜子方法｜证据（子论文里的原句位置）。
2. 同一个缺陷对应两篇以上、思路不同的子方法时，归为一个分歧点，用一句话写出各条思路的根本差别。
3. 检查每个缺陷有没有子方法：没有的，标为“悬空缺陷”，第 5 步要用。

### 第 4 步：属性矩阵

1. **归纳属性。** 把节点表“遗留缺陷”一列里反复出现的说法，改写成能回答“能 / 不能”的能力问题，共 10–15 个。每个属性写一句定义，说明什么情况算 ✓。
2. **相容性预检。** 两两检查属性之间是否逻辑相容（比如“分类任务”和“预测区间”就不相容），把不相容的属性对列成一张表，第 5 步跳过这些组合。

**确认点 2**：把属性定义和相容性表交给用户确认后再填格子。确认之后不再增删属性，以免看到结果后再调整。

3. **填格子。** 论文把这件事当作目标、并用实验证明了的给 ✓；有相关设计但不是主要目标的给 △；其余给 ✗。每个 ✓ 都记下依据（论文的哪一节、哪个实验）。

### 第 5 步：机械地列出候选空白

按以下规则逐条执行，不需要判断力：

- **R1 整列空白**：某个属性整列没有 ✓。△ 不算覆盖，但要在清单里注明“有 △ 部分覆盖”，并列出是哪些方法。回测中 S、V、Z 三列都有 △、没有 ✓，按这条规则判为空白后，三条全部命中；如果把 △ 算作覆盖，这三条都会被漏掉。
- **R2 两两组合空白**：在有 ✓ 的属性中，两两配对，找没有任何一行同时为 ✓ 的组合（等价于 COUNTIFS 结果为 0），跳过第 4 步标为不相容的组合。△ 同样不算覆盖，部分覆盖的情况照样注明。完整版另加 R2′：对有实际需求的组合再检查三元组。
- **R3 悬空缺陷**：第 3 步标出的、没有子方法的遗留缺陷。
- **R4 争议与停滞**：结论互相矛盾的论文对；同一基准上 SOTA 长期没有明显提升；benchmark 的可信度受到质疑。
- **R5 综述的开放问题**：第 1 步记下的 future work 条目。

然后依次过三道筛子：

1. **合并去重**：同一个空白被多条规则命中时合并成一条，在“来源”一列写全所有规则。来源数可以作为排序的参考之一：一次回测中观察到，被两条以上规则同时命中的空白最快被填上。但那三条是被同一篇论文一起填上的，实际只相当于一个样本，还不能当作规律。
2. **需求过滤**：给每条写一句“谁需要它、用在什么场景”。写不出来的删掉，并记入“已过滤”清单。
3. **拼接测试（思想实验）**：如果把两个现成方法简单接起来就能解决，标为“工程问题”，降级处理。只有当两个属性之间存在相互作用、简单拼接会失效时，才算研究问题。写一句为什么会失效。

每条候选归入四类之一：逻辑不成立｜文献里已有但节点表没收录｜简单拼接可解｜疑似真空白。前两类要等第 6 步检索后才能确认。

### 第 6 步：逐条验证（最重要）

正式调研模式下，对每条候选：

1. **三种以上不同说法的检索**：设想解决它的论文标题和摘要会怎么写，用这些词检索。必须覆盖最近 12 个月的 arXiv。
2. **正向追踪**：找到最接近的 2–3 篇工作，逐条查看它们的被引列表，看有没有人接着做完。
3. **最新会议和研讨会**：在最近一届相关顶会的录用列表和 workshop 页面里搜关键词。
4. **跨领域检索**：按第 1 步的邻近领域术语对照表，把候选空白里的本领域术语逐个替换成邻近领域的对应术语，生成检索词再搜一次。回测中唯一的误判，就是因为漏掉了邻近领域早已存在的方法。
5. **判定与置信度**：
    - 判定：确认空白｜部分解决｜已被解决｜争议未决。
    - 置信度：高 = 三种说法 + 正向追踪 + 跨领域都做过，且结论一致；中 = 做了其中两项；低 = 只做了一项，或结论之间有冲突。
    - 每条都写清最接近的工作，以及它们差在哪里。
6. **独立复核**：如果能启动子 Agent，把候选清单交给一个没看过推导过程的子 Agent，只给它一个任务：为每条候选找到“已经解决了它的论文”。它找到的反例优先于本步的判定。
7. **小实验建议**：对“拼接测试”拿不准的候选，写出一个一天以内能完成的验证实验（数据集、基线、指标）。

回测模式下，本步改为：用截止日期之后的论文核对每条候选是否被填上，按事先定好的规则判为命中、部分命中或未命中，并计算截止日期到首次公开日期的间隔。

### 第 7 步：排序

对确认空白和部分解决的候选打分（每项 1–3 分），打分标准在看结果前写下：

- 来源数（被几条规则命中；目前只有一次回测支持，权重不宜过高）
- 需求强度（场景是否具体、是否有人在抱怨）
- 拼接失效程度
- 拥挤度（最近 12 个月相关论文越多，分数越低）
- 可行性（数据、算力、个人技能）

## 5. 输出

1. **开头一段**：结论先行，写明找到几条、各属于哪类、最值得做的两三条是什么。
2. **范围与方法**：输入参数、做了哪些取舍、局限（是否经过独立复核、哪些内容来自已有知识）。
3. **演化图**：Mermaid 格式，边上标注缺陷。节点很多时，改画一张“缺陷 × 时代”的泳道图：每行一个缺陷，从左到右是各时代的解决方法，最后一列用颜色标出是否已解决。
4. **方法节点表、边表与分歧点、属性矩阵**（每个 ✓ 附依据）。
5. **空白清单**：问题陈述｜来源规则｜部分覆盖（△ 及对应方法）｜需求｜拼接测试结论｜最接近的工作及其不足｜判定｜置信度｜排序分｜切入思路或小实验。
6. **已过滤与已被解决的候选**。
7. **检索记录**（附录）。
8. **如实说明**：所有标为「已有知识」、未在本次核对的条目。
9. 读者是人类时，每一节末尾可以附一段【怎么做的】，按步骤说明这一节是怎么得出的，便于读者手动复现。

## 6. 附：回测（第一次用于新领域时推荐）

正式调研前，先把截止日期设在两三年前、规模缩小到 10 个左右的节点跑一遍回测，检查第 4 步选的属性能否“预测”出已知的重要论文。命中率低，说明属性选得不好，先调整属性再做正式调研。
